# PLAN.md — Performance Marketing Dashboard Workbook

Planning document for a personal, "app-like" Excel task tracker / dashboard,
built one sheet at a time. This file is the single source of truth for
design decisions before any implementation happens. Update it every time a
new sheet is planned or a decision changes.

## 1. Overview

- **Goal:** replace scattered work spreadsheets with a single polished
  workbook that acts as a personal task tracker + campaign dashboard for a
  performance marketing role. Should feel like an interactive app, not a
  blank spreadsheet.
- **Target Excel version: 2016 / 2019.** No dynamic arrays, no XLOOKUP,
  FILTER, UNIQUE, SORT, or LAMBDA. All formulas must use legacy-safe
  functions: `INDEX`/`MATCH`, `SUMIFS`/`COUNTIFS`, `SMALL`/`LARGE`, and real
  Excel Tables (ListObjects) for structured references.
- **Macro policy: VBA is allowed** (workbook will be `.xlsm`). Used sparingly
  for real interactivity (buttons, forced recalculation, later: automation
  like archiving) — not required for the core data automation, which is all
  formula-driven.
- **Visual design system:** every sheet's colors, typography, iconography,
  and layout conventions follow a single cross-cutting system — see §17,
  [[Visual Design System]] — rather than each sheet inventing its own.
- **Build approach:** the workbook is generated by a Python build script
  rather than built by hand.
  - `openpyxl` (already installed — v3.1.5, Python 3.14.6) builds the
    structure: sheets, formulas, number formats, conditional formatting,
    data validation, Excel Tables, charts.
  - `openpyxl` cannot write VBA. Macro injection is a separate step using
    `pywin32` (COM automation driving a locally installed Excel) — install
    later with `pip install pywin32`. Requires "Trust access to the VBA
    project object model" enabled once in Excel's Trust Center **on the
    machine used to build the file**. Does not affect opening the finished
    `.xlsm` at work.
  - The script is the source of truth and gets re-run to regenerate/update
    the file as more sheets are designed.

## 4. Dashboard sheet spec

### A. KPI summary strip (top of sheet, card-style cells)

| KPI | Formula approach |
|---|---|
| Active Tasks (Upcoming) | `COUNTA(Tasks!ID)` — count of all rows in `Tasks`. Nothing "Completed" ever remains there (see §6.5: completed tasks move to `Archive` immediately). |
| Completed Tasks (Total) | `COUNTA(Archive!ID)` — sourced from `Archive`, not `Tasks`. |

| Overdue Tasks | `COUNTIFS(Tasks!DaysLeft,"<0")` — red fill via conditional formatting when > 0 |
| Current Campaign Ends (countdown) | nearest Active campaign's End Date − TODAY(), via helper column + `SMALL`/array `MIN(IF(...))`, from `Campaigns` |

> once `Tasks` was designed, completed tasks turned out to auto-archive

### B. Upcoming Tasks (Next 5 Deadlines)

Columns: ID, Task, Project, Priority, Deadline, Days Left.

Legacy-safe "top N" extraction (no dynamic arrays available): add a helper
column on `Tasks`, `SortKey = Deadline + TaskKey/1e6` — keeps values unique
and sortable so ties don't collide. On Dashboard, use
`SMALL(Tasks!SortKey, k)` + `INDEX`/`MATCH` for k = 1..5. Conditional
formatting highlights rows with Days Left ≤ 2.

> **Corrected from the original draft:** the tie-breaker originally used
> `ID/1e6`, which assumed a numeric ID. `Tasks` IDs are hierarchical text
> (`"1.2.3"`) — the tie-breaker now uses the hidden numeric `TaskKey`
> instead (see [[Tasks sheet spec]]).

### C. Yearly Monthly Performance

12 rows (Jan–Dec), columns: Month, Completed, Hours.
`COUNTIFS`/`SUMIFS` on `Archive` (not `Tasks` — completed tasks live there,
stamped with `Completed At` at archive-time) filtered by
`MONTH(Completed At)` and `YEAR(Completed At) = YEAR(TODAY())`
(currently resolves to 2026). Feeds the chart in section D.

### D. Daily & Weekly Productivity

Table — columns: Productivity Indicator/Metric, Performance/Duration. Rows:
- Completed Tasks Today
- Time Invested Today
- Completed This Week
- Time Invested This Week

"Completed Tasks Today/This Week" use `COUNTIFS`/`SUMIFS` on `Archive!Completed At`
with `TODAY()` and week-start/week-end bounds (via `WEEKNUM` or explicit
Monday-start date math). "Time Invested Today/This Week" are `SUMIFS` against
the hidden `Time Log` sheet (TaskKey, Date, Duration) by date — a single
running `Time Spent` total per task can't answer "how much today vs. this
week," so each timer stop logs a dated entry there (see [[Tasks sheet

Plus an embedded `openpyxl` chart (line or column) plotting the Yearly
Monthly Performance table (Completed and Hours by month) for 2026.

### E. Marketing Campaign Reminders (7-Day Window)

Columns: Campaign Name, Start Date, End Date, Days Left, Status. Same

## 6. Tasks sheet spec

The most important sheet in the workbook: a gamified, self-organizing
checklist with unlimited-depth subtasks, auto-calculated hierarchical IDs,
a double-click deadline picker handing off to `Calendar`, a double-click
work timer, and automatic archiving/deletion driven by the `Status`
dropdown.

Confirmed decisions:
- **Days Left** = `Deadline − TODAY()` (days remaining, countdown-style,
  consistent with the Dashboard).
- **Hierarchy depth is truly unlimited** — not capped at Excel's native
  8-level Group/Outline limit. Collapse/expand is a **custom VBA
  double-click mechanism** (no native +/- gutter buttons).
- **Completing a parent with open subtasks auto-cascades**: marking a
  parent "Completed" automatically marks all its subtasks "Completed" too,
  and the whole branch archives together.
- **Only one timer can run at a time**: starting a timer on a task
  auto-stops whichever other task's timer was running.

### 6.2 Key architecture decisions (technical necessities beyond the user's literal spec)

1. **Hidden stable `TaskKey` + `ParentKey` columns.** The user types a
   parent's *visible* ID (e.g. "1.2") into `Subtask of`. Visible IDs shift
   when tasks are added/deleted/reordered, so they're unsafe as a permanent
   internal reference. Every row gets a hidden, never-reused `TaskKey` (a
   monotonic counter) assigned once at creation. When the user types a
   `Subtask of` value, a macro resolves it to the parent's current
   `TaskKey` and stores that — the *displayed* `Subtask of` text is a
   read-only, macro-refreshed label (always shows the parent's current
   visible ID), not the source of truth.
2. **Renumbering also reorders rows into outline order.** When a task is
   (re)parented, its row is physically moved directly after its parent's
   last existing descendant, so the sheet always reads top-to-bottom as a
   proper indented tree, and collapse/expand can simply hide/show a
   contiguous row block. `RenumberHierarchy()` walks the *entire* tree and
   reassigns every visible `ID` from scratch each time it runs — it never
   patches IDs incrementally. Since it's called after every structural
   change (§6.3), cascading renumbering after an archive or delete is an
   automatic consequence, not a separate mechanism: if `1.1` completes and
   archives, `1.2` (and any of its own descendants) becomes `1.1` on the
   next pass; if `1` itself completes and archives, `2` becomes `1` and
   `2.1` becomes `1.1`.
3. **`Number of Subtasks` is a live formula, not VBA**, once IDs follow the
   `1.2.3` convention: `=COUNTIF(ID_range, [@ID] & ".*")` counts all
   descendants at any depth via prefix wildcard match — no recursion
   needed.
4. **A new hidden internal time log is required.** A single running "Time
   Spent" total per task can't answer "how much today vs. this week" for
   the Dashboard. Add a hidden sheet `Time Log` (TaskKey, Date, Duration),
   appended to on every timer stop — see the sheet index (section 2).
5. **`Linked Campaign` resolves by hidden key, same pattern as `Subtask
   of`.** The user picks a campaign by name from the dropdown; a macro
   resolves it to the campaign's hidden `CampaignKey` (see [[Campaigns
   sheet spec]] §10) and stores that — the displayed name is a refreshed
   label, not the source of truth. Display lookups span both `Campaigns`
   and `Campaigns Archive` by key, so a task linked to an already-completed
   campaign still shows the right name.
6. **`SiblingOrder` makes manual reordering possible.** Sibling order was
   previously only ever "append at the end" (implicit in row position at
   creation/reparenting time), with no way to reorder afterward. A hidden
   numeric `SiblingOrder` column, assigned in increments (e.g. 10, 20,
   30...) at creation/reparenting (`max(existing siblings) + 10`), gives
   `RenumberHierarchy()` an explicit, adjustable tiebreaker for ordering
   children of the same parent. The `↑`/`↓` columns (§6.1) swap this value
   between adjacent siblings to move a task (and its whole subtree) up or
   down without reparenting it.

### 6.3 VBA architecture for this sheet

The most macro-heavy sheet in the workbook. Routines needed:

- **`Worksheet_Change`** dispatcher on Tasks, branching on which column
  changed:
  - Task name filled in (was blank) → stamp `Start Date = Now()`.
  - `Subtask of` edited → resolve `ParentKey`, reposition row, call
    `RenumberHierarchy`.
  - `Linked Campaign` edited → resolve to hidden `LinkedCampaignKey`
    (looked up against `Campaigns`' current `CampaignKey` list by name),
    keep the displayed text refreshed to the campaign's current name.
  - `Status → Completed` → cascade-complete all open descendants, copy the
    whole branch to `Archive` (static values, per the archiving macro in
    §7) with a stamped `Completed At`, delete from `Tasks`, call
    `RenumberHierarchy`.
  - `Status → Delete` → confirm via a `MsgBox` (destructive/irreversible),
    then cascade-delete the row and all descendants, call
    `RenumberHierarchy`.
- **`Worksheet_BeforeDoubleClick`** dispatcher on Tasks, branching on
  column:
  - `Deadline` cell → set the generic Calendar handoff (see §8):
    `HandoffOriginSheet = "Tasks"`, `HandoffKey = ` this row's `TaskKey`,
    `HandoffKeyColumn = "TaskKey"`, `HandoffTargetColumn = "Deadline"`,
    navigate to `Calendar`, `Cancel = True`.
  - `Timer` cell → if another task's timer is running, stop it first (log
    + accumulate its time); toggle this task's timer on/off, stamping/
    clearing `TimerRunningSince` and appending to `Time Log` on stop. On
    start, also set this row's `Status` to "In Progress" if it isn't
    already (a task can't be "Completed" while still in `Tasks`, so no
    conflict there). `Cancel = True`.
  - `Task` cell on a row with subtasks → toggle `Rows.Hidden` for its
    descendant row block (collapse/expand). `Cancel = True`.
  - `Notes` cell → load the `frmNotes` popup (see below), pre-filled with
    the cell's current text; remember the originating cell so OK can write
    back to the right place. `Cancel = True`.
  - `↑` cell → swap `SiblingOrder` with the immediately preceding sibling
    (same `ParentKey`), call `RenumberHierarchy`. No-op if already first.
    `Cancel = True`.
  - `↓` cell → swap `SiblingOrder` with the immediately following sibling,
    call `RenumberHierarchy`. No-op if already last. `Cancel = True`.
- **`frmNotes` popup** (Notes editor): a VBA UserForm with a large
  multi-line `TextBox` (pastel-yellow background, sticky-note feel) and a
  size-toggle button that swaps the form between two preset sizes (compact
  ≈ 280×220 px, expanded ≈ 480×420 px — plain VBA property changes, no
  Windows API resize hacks, to stay safe in a locked-down environment). OK
  writes the TextBox content back to the originating `Notes` cell and
  closes; Cancel (and `Esc`) discards edits. The cell's real value is the
  full note text — a custom number format displays it as a 📝 icon when
  non-empty and blank when empty, so the underlying text stays in the cell
  itself (searchable, no extra hidden column) while the row stays clean.
- **`RenumberHierarchy()`** — the core engine: walks the tree via
  `ParentKey`, reorders rows into depth-first outline order, assigns
  visible `ID` text and `Level`, sets indentation/shading, refreshes
  displayed `Subtask of` labels. Called after any structural change.
- **Calendar's `✓ Confirm` button macro** (see §8 for the full Calendar
  design): reads the generic handoff set above, looks up the row in
  `Tasks` where `TaskKey` matches `HandoffKey` (not row number, since rows
  may have moved), writes the chosen date+time into that row's `Deadline`
  cell, navigates back to Tasks and selects the cell.
- Workbook-open check (extends the Dashboard's `Workbook_Open` macro): if
  `TimerRunningSince` is non-blank for any task on open, warn the user a
  timer was left running when the file was last closed.

### 6.4 Gamified/visual treatment

- Status shown with icon-style cues (e.g. ⬜ Not Started, 🔄 In Progress) via
  conditional formatting / custom number format, not a real ActiveX
  checkbox (more portable in a locked-down environment).
- Priority as colored chips (dropdown-driven conditional formatting).
- Depth-based indentation (native cell indent) + progressively lighter row
  shading per level, so nesting is readable without visual clutter.
- Data-bar style progress indicator on `Number of Subtasks` reflecting how
  many descendants are done vs. open, for parent tasks.
- Running timer gets a distinct highlight (e.g. green fill + "▶ Running")
  so it's always obvious a clock is ticking somewhere.

### 6.5 What Tasks feeds into the Dashboard

- Active Tasks (Upcoming) → count of all rows in `Tasks` (nothing
  "Completed" remains there — it moves to `Archive` immediately).
- Overdue Tasks → `Tasks` rows where `Days Left < 0`.
- Upcoming Tasks (Next 5 Deadlines) → `Tasks`: ID, Task, Project, Priority,
  Deadline, Days Left; tie-break by `TaskKey`, not ID text.
- Total Hours Invested → `SUM(Tasks!TimeSpent) + SUM(Archive!TimeSpent)`.
- Time Invested Today / This Week → aggregated from the hidden `Time Log`
  sheet (`SUMIFS` by date), not from `Time Spent` directly.
- Completed Tasks (Total) and Yearly Monthly Performance (Completed, Hours
  by month) → sourced from `Archive` (with its stamped `Completed At`),
  not `Tasks`.

## 7. Archive sheet spec

Where completed task branches land automatically when marked "Completed" on
`Tasks` (per the cascade-archive behavior in §6.3). Mirrors `Tasks`' columns
minus the interactive `Timer`, plus a new `Completed At` column at the end.
Unlike `Tasks`, this is a **flat historical log, not an interactive tree**:
archived branches are appended as plain rows with hierarchy captured as a
static visual snapshot (indentation preserved via the hidden `Level` value),
but no live collapse/expand or renumbering logic — it's a record to browse,
not a workspace.

### 7.1 Columns

| Column | Behavior |
|---|---|
| ID | Static snapshot of the task's ID text at archive time (not live — may repeat across different archived batches since Tasks IDs are tree-position-relative, not globally unique; the hidden `TaskKey` remains the true unique identifier). |
| Start Date | Static, copied as-is from `Tasks`. |
| Task | Static, copied as-is. Indentation copied as a static snapshot (via the hidden `Level` value) so the branch's former shape is still visually readable. |
| Number of Subtasks | Static snapshot count at archive time (frozen — a completed branch never gains new subtasks). |
| Subtask of | Static snapshot of the displayed parent ID text at archive time. |
| Project / Category | Static, copied as-is. |
| Linked Campaign | Static text (the campaign's name at archive time, not the live-resolving key `Tasks` uses) — preserves which campaign an archived task was linked to, as historical record. |
| Priority | Static, copied as-is (color chip formatting still applies for readability). |
| Deadline | Static, copied as-is. |
| Status | Always "Completed" for every row here (a "Delete" never reaches Archive). |
| Days Left | Frozen at archive time as `Deadline − Completed At` ("days early/late at completion"): positive = finished early, negative = finished late. |
| Time Spent | Final static total time logged before completion (copied as-is — already a plain accumulating value on `Tasks`, not a formula). |
| Notes | Same storage/display as `Tasks`: real cell value + custom-number-format 📝 icon; double-click still opens `frmNotes` to view/edit. Reused, not reimplemented. |
| **Completed At** *(new, last column)* | Date + time stamp (`Now()`) written by the archiving macro at the moment the branch moves. |

> this section was originally written before `Linked Campaign` existed as a
> `Tasks` column at all (Campaigns was planned in a later session), so
> Archive never got updated to preserve it — an archived task would have
> silently lost its campaign link. Added `Linked Campaign` as static text
> (unlike `Tasks`, which resolves it live by key) for the same reason
> `Priority`/`Project / Category` are preserved: historical record.
>
> Also confirmed with the user: **the Archive sheet is protected** (locked
> against direct cell edits) since Dashboard's historical stats read
> straight from it — an accidental edit to a `Time Spent` value would
> silently skew "Total Hours Invested." Every cell stays locked uniformly
> (nothing is meant to be typed directly here, including `Notes`, which
> still goes through `frmNotes` same as `Tasks`). Basic sheet protection is
> set structurally in Phase 2, but `UserInterfaceOnly:=True` (which lets
> VBA keep writing while blocking direct typing) does **not** persist
> across file close/reopen — Phase 3 must re-assert it on `Workbook_Open`,
> or the archiving macro's own writes would be blocked too.
>
> **Live-tested finding (Phase 2):** `UserInterfaceOnly:=True` lets VBA
> write plain cell values on a protected sheet, but Excel disables
> `ListObject`/Table operations entirely while protection is active —
> `ListRows.Add` fails with "Table functions are not available because the
> sheet is protected," even combined with `Protect ...,
> AllowInsertingRows:=True` (confirmed not to fix it). The archiving macro
> (Phase 3) must explicitly `Unprotect` → append the row (`ListRows.Add` +
> populate cells) → `Protect ..., UserInterfaceOnly:=True` again around
> just that operation, rather than relying on any protection-flag
> combination to allow it directly.

`Timer` is intentionally omitted (no interactive timer on a completed task).
Hidden helper columns retained: `TaskKey`, `ParentKey`, `Level` (for the
static indentation snapshot). `TimerRunningSince` is dropped — not needed
once Timer itself is gone.

### 7.2 Mechanics

- **Archiving macro** (the destination side of the `Status → Completed`
  handler in §6.3): for each row in the completed branch, in existing
  depth-first order, copy static *values* (not formulas) for every shared
  column, write `Completed At = Now()`, compute frozen
  `Days Left = Deadline − Completed At`, skip `Timer`, append to the bottom
  of `Archive`. This happens as part of the same operation that deletes the
  branch from `Tasks` and calls `RenumberHierarchy` there — no separate
  trigger needed on the Tasks side.
- **Archive's own VBA is minimal**: just a `Worksheet_BeforeDoubleClick`
  handler for the `Notes` column (reusing `frmNotes`, same as Tasks). No
  hierarchy engine, no collapse/expand, no renumbering — rows are
  append-only and never reordered.

### 7.3 What Archive feeds into the Dashboard

- **Completed Tasks (Total)** → `COUNTA(Archive!ID)`.
- **Yearly Monthly Performance** (Completed count + Hours by month) →
  `COUNTIFS`/`SUMIFS` on `Archive!Completed At`, grouped by month/year.
- **Completed Tasks Today / This Week** → `COUNTIFS` on
  `Archive!Completed At` against `TODAY()` / week bounds.
- **Total Hours Invested** → `SUM(Tasks!TimeSpent) + SUM(Archive!TimeSpent)`.
- *(Not yet wired into a Dashboard metric — see Open Questions)*: the frozen
  `Days Left` ("early/late at completion") could feed a future

## 8. Calendar sheet spec

The destination of the Deadline double-click handoff from `Tasks` (and,
once planned, other date-pickers elsewhere in the workbook). Looks and
behaves like a real calendar app: a correct month grid (day-of-week
alignment, leap years handled) with prev/next month navigation, plus the
date+time picking flow. Week starts on **Monday**. Days with a matching
`Tasks!Deadline` show a live event marker (extended to `Campaigns`
start/end dates once that sheet is planned), so it reads as a real calendar
at a glance, not just a bare date-picker.

### 8.1 Generic handoff contract

Any sheet that wants to use the Calendar picker sets these four values
before navigating to `Calendar`:
- `HandoffOriginSheet` — e.g. `"Tasks"`.
- `HandoffKey` — the stable key value (e.g. a `TaskKey` number).
- `HandoffKeyColumn` — which hidden column holds that key on the origin
  sheet (e.g. `"TaskKey"`).
- `HandoffTargetColumn` — which column to write the picked value into
  (e.g. `"Deadline"`).

Calendar's confirm macro is generic: look up the row in
`HandoffOriginSheet` where `HandoffKeyColumn` = `HandoffKey`, write the
picked datetime into `HandoffTargetColumn` of that row. Generalized now
(rather than staying Tasks/`TaskKey`-specific) since nothing is built yet —
free to design correctly up front, and it lets `Campaigns` (Start/End Date)
or `Recurring Tasks` reuse the same picker later without rework. Tasks'
Deadline double-click handler (§6.3) already sets these four values.

### 8.2 Layout and navigation

- **Header:** month/year label (e.g. "July 2026"), `◀ Prev` / `▶ Next`
  month buttons, a `Today` button to jump back to the current month.
  Navigation only changes which month is displayed
  (`SelectedYear`/`SelectedMonth` cells) — browsing to a different month
  doesn't disturb an in-progress date pick.
- **Grid:** classic 7-column (Mon–Sun) × up to 6-row month grid, entirely
  formula-driven off `SelectedYear`/`SelectedMonth` (`DATE`, `WEEKDAY`
  arithmetic — legacy-safe, no VBA needed to regenerate the grid).
  Leading/trailing days from adjacent months shown grayed out via
  conditional formatting (`MONTH(cell)<>SelectedMonth`). Today's date gets
  a distinct highlight border. Days with a matching `Tasks!Deadline`
  (date-only comparison) get a small marker via conditional formatting
  (`COUNTIFS` date-range match).

### 8.3 Date + time selection

- Double-click a day cell (`Worksheet_BeforeDoubleClick`, dispatched when
  inside the grid range) → sets a hidden `SelectedDate` cell, highlights
  that cell (clearing any previous selection), `Cancel = True`.
- `Hour` (00–23) and `Minute` (00/15/30/45) dropdowns next to the grid
  (Data Validation lists) combine with `SelectedDate` into a
  `SelectedDateTime` formula cell.
- A small live preview label shows the full selection in friendly text
  (e.g. "Thursday, 16 July 2026 — 14:30") before confirming.

### 8.4 Buttons

- **`✓ Confirm`** — writes `SelectedDateTime` to the handoff target (§8.1),
  clears the handoff, navigates back to the origin sheet/cell. If no
  handoff is pending (Calendar opened directly, just to browse), shows a
  brief message instead of erroring.
- **`✕ Cancel`** — clears the handoff and navigates back without writing
  anything.

### 8.5 Visual/gamified treatment

Consistent with the rest of the workbook: colored month/year header
banner, weekend columns lightly shaded, today's cell and the selected cell
each with a distinct accent color, event-marker dots in a contrasting
color, no gridlines outside the day grid for a clean "app" look.

### 8.6 VBA routines needed

`GoToPrevMonth()`, `GoToNextMonth()`, `GoToToday()` (adjust
`SelectedYear`/`SelectedMonth`); `Worksheet_BeforeDoubleClick` (day-cell
selection); `ConfirmButton_Click()` (generic handoff write-back +
navigate); `CancelButton_Click()` (clear handoff + navigate back). No
hierarchy/renumbering engine needed — this sheet has no tree structure.

### 8.7 Dashboard contribution

None — Calendar is a utility/picker UI, not a data source (unlike
Tasks/Archive).

## 12. Recurring Tasks sheet spec

Templates for Daily/Weekly/Monthly tasks that, when Active, automatically
generate real rows into `Tasks` on their schedule. Missed occurrences get
backfilled on next open rather than silently skipped; templates get the
**full** hierarchy engine (mirroring `Tasks`' own tree — unlimited-depth
subtasks, collapse/expand, `↑`/`↓` reorder); new instances always generate
on schedule regardless of whether an earlier instance is still open in
`Tasks`.

### 12.1 Watermark-based generation

Each **root-level** template row (`Subtask of` blank — subtasks inherit
their parent template's schedule, they don't have their own) gets a hidden
`LastGeneratedThroughDate`. On `Workbook_Open`, `RegenerateRecurringTasks()`
walks all Active root templates and, for each, computes every scheduled
occurrence date strictly after `LastGeneratedThroughDate` up through
`TODAY()` (Daily = every date; Weekly = dates matching the chosen weekday;
Monthly = dates matching the chosen day-of-month, clamped to the last day
of shorter months). This single rolling watermark unifies the "just one
new occurrence since yesterday" case and the "haven't opened this in
weeks" backfill case — no separate log of individual generated dates
needed.

**Safety cap**: if more than a proposed 30 occurrences are pending for a
single template, only the most recent 30 generate; a `MsgBox` warns how
many older occurrences were skipped, and the watermark still advances past
all of them (so they aren't retried forever). Tunable default (§5).

For each occurrence date (oldest → newest), the macro deep-copies the
template's entire branch (root + all subtasks at every depth) into
`Tasks`: fresh `TaskKey`s, `ParentKey` structure remapped to match, `Start
Date` = the occurrence date, `Deadline` = occurrence date + that row's own
`Deadline Offset` (each row in the branch can have its own offset, same as
`Priority`), `Status` = "Not Started", `Priority`/`Project/Category`/
`Linked Campaign`/`Notes` copied from the template. After all instances for
a template are generated, `Tasks!RenumberHierarchy()` runs once to
position and ID the newly inserted branches. Toggling a template
`Inactive` simply pauses generation (watermark frozen); reactivating later
triggers catch-up for the whole gap, same safety cap applies.

### 12.2 Hierarchy engine

Same `RenumberHierarchy`-equivalent, `↑`/`↓` reorder, collapse/expand, and
`Subtask of`/key-resolve mechanics as `Tasks` §6.2/§6.3 — this sheet gets
its own independent tree (own key/ID sequence, unrelated to `Tasks`' own),
built the same way.

### 12.3 `Task Start On`: dynamic dropdown via Data Validation formula, no VBA

Its Data Validation source is a formula keyed off that row's `Recurrence`
cell (`INDIRECT(IF(Recurrence="Weekly","WeekdayList",
IF(Recurrence="Monthly","DayNumberList","")))`, pointing at two named
lists) — legacy-safe, no VBA needed to swap the dropdown options as
`Recurrence` changes. Blank/disabled for `Daily`. A day-of-month chosen for
`Monthly` that doesn't exist in a given month (e.g. 31 in February) clamps
to that month's last day.

### 12.4 Columns

Status placed first, per explicit instruction:

| Column | Behavior |
|---|---|
| Status | Dropdown: Active, Inactive. Color-coded chip. |
| ID | Own hierarchical text ID, independent from `Tasks`' ID sequence. |
| ↑ / ↓ | Same reorder-among-siblings mechanic as `Tasks` §6.1. |
| Task | Free text, indented per depth. |
| Number of Subtasks | Live formula, same ID-prefix pattern as `Tasks`. |
| Subtask of | Same resolve-by-key pattern as `Tasks`. |
| Project / Category | Free text. |
| Linked Campaign | Same optional dropdown/resolve mechanism as `Tasks` (kept for consistency — a recurring task can optionally pre-link to a campaign). |
| Priority | Dropdown (Low/Medium/High), color chip — carries into generated instances. |
| Recurrence | Dropdown: Daily, Weekly, Monthly. Color-coded chip. |
| Task Start On | Blank for Daily; weekday dropdown for Weekly; day-of-month (1–31) for Monthly (dynamic dropdown, §12.3). |
| Deadline Offset (days) | User-typed number. Generated instance's `Deadline` = its `Start Date` + this offset. |
| Notes | Same `frmNotes` popup mechanism as `Tasks`. |

Hidden: `RecurringKey`, `RecurringParentKey`, `Level`, `SiblingOrder`,
`LinkedCampaignKey`, `LastGeneratedThroughDate` (root-level rows only).

**Dropped from `Tasks`' column set** (don't apply to a template, replaced
by the above): `Start Date` (replaced by `Recurrence`/`Task Start On`),
`Deadline` (replaced by `Deadline Offset`), `Days Left`, `Timer`, `Time
Spent` (nothing to time-track on a template itself — tracking happens on
the generated `Tasks` instance), and the original `Status` dropdown
(Not Started/In Progress/Completed/Delete — replaced entirely by
Active/Inactive here).

### 12.5 Dashboard contribution

None directly — Recurring Tasks generates rows into `Tasks`, which already
feeds the Dashboard.

## 13. Schedule + Schedule Data sheet spec

A visual work-location/meetings calendar (`Schedule`) backed by raw storage
(`Schedule Data`). Reuses `Calendar`'s (§8) month-grid mechanism as the
visual base, and introduces the workbook's first *timer-driven* automation
— pop-up meeting reminders via `Application.OnTime` — rather than
something triggered by opening/editing/double-clicking.

Confirmed decision: **reminders count down toward the meeting** — "X
minutes before" is the first reminder, and additional reminders count down
closer to meeting start (e.g. first=10, count=3, interval=5 → reminders at
10, 5, and 0 minutes before).

### 13.1 Schedule Data (storage — two tables)

- **Work Location**: `Date`, `Location` (dropdown: Home Office, Office,
  Holiday — color-coded).
- **Meetings**: `Meeting Name`, `Start Time`, `End Time`, `Recurrence`
  (dropdown: One-time, Daily, Weekly, Monthly), `Anchor Date` (the date the
  meeting was created on — for one-time meetings this *is* the meeting
  date; for recurring ones, its weekday/day-of-month defines the pattern),
  `Status` (Active/Inactive, mirrors [[Recurring Tasks sheet spec]] §12).
  Hidden `MeetingKey` (stable, monotonic — so the popup's "remove meeting"
  action can reliably target the right row as others are added/removed).

### 13.2 Schedule (visual calendar)

Reuses `Calendar`'s (§8.2) month-grid mechanism directly — Monday-start,
`DATE`/`WEEKDAY`-driven, prev/next/today navigation. Each day cell:
background color-coded by that date's Work Location (live lookup into
Schedule Data), plus a small meeting-count badge (live formula: one-time
meetings matching that exact date + Active recurring meetings whose
pattern matches that date's weekday/day-of-month).

### 13.3 Double-click day popup (`frmScheduleDay`)

Double-clicking a day cell (`Worksheet_BeforeDoubleClick`, same language as
`Calendar`) opens a popup with:
- A `Work Location` dropdown for the clicked date (pre-filled if already
  set); Save writes/updates that date's row in Schedule Data.
- A compact read-list of meetings occurring on that date (one-time on that
  exact date + recurring matching its weekday/day-of-month), each with a
  simple "Remove" control (single click, no confirmation — low-stakes
  personal scheduling, unlike the destructive-delete confirmations
  elsewhere in the workbook).
- An "Add Meeting" mini-form in the same popup: `Meeting Name`, `Start
  Time`/`End Time` (Hour/Minute dropdowns, same pattern as `Calendar`
  §8.3), `Recurrence` dropdown. **If recurring, the clicked date's own
  weekday/day-of-month becomes the anchor pattern automatically** — no
  separate "start on" field needed (simpler than [[Recurring Tasks sheet
  spec]] §12.3's dynamic dropdown, since the popup's context already *is*
  the anchor date). Save appends a row to Schedule Data's Meetings table.

### 13.4 Recurring meetings: dynamically evaluated, never physically duplicated

Unlike Recurring Tasks (which generates real, independently-trackable rows
into `Tasks`), a meeting doesn't need per-occurrence state — there's
nothing to individually complete or archive. A recurring meeting stays a
**single rule row**; "does meeting X occur on date D" is a live formula
check (Recurrence type + Anchor Date's weekday/day-of-month, only while
Active) used both for calendar display and for reminder scheduling. No
watermark, no backfill, no generation engine needed here.

### 13.5 Reminders (`Application.OnTime`)

- **Global settings** (not per-meeting — matches "I would be able to set,"
  singular, and the precedent set by Monthly Media Plan's single
  exchange-rate setting): `ReminderFirstOffset` (minutes before, default
  10), `ReminderCount` (default 1), `ReminderInterval` (minutes). Set via a
  small settings popup (`frmReminderSettings`), same pattern as Monthly
  Media Plan's exchange-rate button (§9.4).
- **`ScheduleReminders()`**: runs on `Workbook_Open` and whenever the
  Meetings table changes (`Worksheet_Change` on Schedule Data). Cancels any
  previously scheduled `Application.OnTime` calls (tracked in a hidden
  list, so stale/duplicate timers don't accumulate), recomputes today's
  remaining meetings (one-time today + Active recurring matching today's
  pattern), computes each one's reminder times per the settings (counting
  down toward the meeting), and schedules `Application.OnTime` for each one
  still in the future.
- **`Workbook_BeforeClose`**: cancels all pending scheduled reminders, so
  Excel doesn't error or attempt to reopen the file later to fire a stale
  timer.
- **`frmMeetingReminder`** popup (not a bare `MsgBox`, for consistency with
  the rest of the workbook's polish): shows meeting name, start time,
  minutes-until-start; OK dismisses. Fires workbook-wide regardless of
  which sheet is active — `Application.OnTime` is a global Excel timer, not
  sheet-scoped, which is exactly the desired behavior.
- **Inherent limitation**: reminders only fire while the workbook is
  actually open in Excel — no reminders if closed, and no backfill concept
  applies (a reminder for an already-passed meeting is meaningless). See §5.

### 13.6 Dashboard contribution

None currently — see §5 for a possible future addition.

## 17. Visual Design System

A single, cross-cutting system for color, typography, iconography, and
layout that every sheet spec in this document draws from, rather than each
sheet inventing its own "color-coded chip" treatment independently. Built
using the `dataviz` skill's color methodology (categorical / status /
sequential / diverging, each validated rather than eyeballed).

### 17.1 Two separate palette roles

- **Brand/chrome accent — brand blue (`#1428A0`), white text only.**
  Used for structural elements: sheet header bands, primary buttons
  (`✓ Confirm`, `🔄 Start New Month`, etc.), sheet-tab color, Dashboard card
  accent borders. Verified via contrast check: white text on brand blue
  = 11.4:1 (clears WCAG AAA); brand blue vs. the light page surface =
  10.8:1. Black text on brand blue fails (1.7:1) — white text is
  mandatory on any brand-blue fill.
- **Data palette — the validated default 8-hue categorical set**, kept
  as-is for identity chips (dropdown values like Platform, Funded,
  Optimization): blue `#2a78d6`, aqua `#1baf7a`, yellow `#eda100`, green
  `#008300`, violet `#4a3aa7`, red `#e34948`, magenta `#e87ba4`, orange
  `#eb6834`. These 8 hues were chosen and *ordered* together as a set
  (worst adjacent CVD ΔE 24.2, well above the ≥12 target) — swapping just
  one slot for the brand blue would break that balance. Brand color =
  structure; data palette = encoding — a deliberate separation, not an
  oversight.

### 17.10 Modernization pass (user-requested, PLAN.md §19 Phase 6)

After the full §17 audit above (Phase 6's first checklist item) passed
clean, the user reviewed the file and said it still "feels a bit aged...
like a spreadsheet from 2008" and asked to brainstorm modernizing it.
Root-caused before proposing anything: every one of the workbook's 8
`ListObject` Tables used the built-in `TableStyleMedium2` style — Excel's
own stock banded-blue table style, unchanged since Office 2007 — whose
own blue/white row banding was visually fighting the workbook's custom
brand-blue header band, plus Excel's own stock chrome (row/column
letter headers, 100% zoom, ~15pt default row height) never having been
touched. Confirmed with the user via a 6-item proposal; they chose to do
all six:

1. **Replace `TableStyleMedium2` with a quiet, hand-rolled table
   treatment.** `design_system.modern_table_style()` returns a
   `TableStyleInfo(name=None, ...)` — Excel renders the table with *zero*
   built-in styling (no banding, no borders) once no named style is set,
   verified empirically (`ListObject.TableStyle` reads back blank, file
   opens with no repair prompt). Replaces it with our own two pieces:
   `conditional_formatting.row_banding_rule()` (a single `MOD(ROW()-
   first_row,2)=0` CF rule using the existing `PAGE_BG` token, aliased
   here as `TABLE_STRIPE`) and `design_system.apply_table_hairline_
   borders()` (a direct bottom-only `Border(style="hair", color=
   GRIDLINE)` per body cell — no vertical borders, no top border; a
   single bottom rule per row already reads as separation without the
   boxed-in classic-grid look). **Applied differently depending on table
   size**: the two genuinely unbounded, ever-growing tables (`Archive`,
   `Campaigns Archive`) get banding only, across a generous 1000-row CF
   range matching their own existing CF-range convention — a direct
   per-cell `Border` object on 1000 rows × ~17 columns would be real file
   bloat, unlike a CF rule which is stored once regardless of range size.
   The fixed 50-row (or smaller) reference tables (`Login Information`,
   `Quick Links`, `Monthly Media Plan`, `Schedule Data`'s two tables, and
   Dashboard's five small tables via its shared `_add_table()` helper)
   get both banding and hairline borders, since a bounded small range
   makes the per-cell cost negligible.
   > Verified via COM that the new banding CF correctly loses to any
   > pre-existing status-color CF on the same cell (e.g. Login
   > Information's Access `Yes`/`No` green/gray) rather than overriding
   > it — `conditional_formatting.apply_rules()` always adds the
   > status-color rule *before* the banding rule for any sheet that has
   > both, and openpyxl assigns CF priority in add-order (earlier add =
   > lower priority number = wins), confirmed by reading back
   > `DisplayFormat.Interior.Color` on a banded row's Access cell and
   > getting the status green, not the banding gray.
2. **Hide Excel's own row/column letter headers**, via `sheet_view.
   showRowColHeaders = False` (a real per-sheet, file-persisted OOXML
   setting — no VBA needed, unlike the formula bar below) — folded into
   the new `design_system.apply_modern_chrome()` helper alongside
   gridlines-off, replacing what used to be a bare `showGridLines =
   False` line in all 12 visible sheets' `build()` (`Time Log` stays
   untouched — `veryHidden`, never rendered to the user).
   **Also hide the formula bar** — `Application.DisplayFormulaBar`,
   unlike row/column headers, is a genuine **Excel-wide** Application
   setting, not saved per-workbook at all. Toggling it once in
   `Workbook_Open` would leak into every *other* workbook the user has
   open in the same Excel session — an unacceptable side effect for a
   personal productivity tool the user keeps open alongside other work.
   Scoped instead to `Workbook_Activate`/`Workbook_Deactivate` in
   `ThisWorkbook.bas`, so the formula bar only disappears while this
   workbook is the active window and comes back the instant focus moves
   elsewhere — verified via COM with a real second workbook: `True` →
   open dashboard → `False` → open a 2nd workbook → `True` (correctly
   restored) → close the 2nd workbook → `False` again (correctly
   re-hidden on refocus). `Workbook_BeforeClose` also sets it `True` as a
   backstop. **Known limitation, accepted rather than chased further**:
   closing the *only* open workbook (zero workbooks left in that Excel
   process) leaves it `False` instead of restoring `True` — confirmed via
   COM the `BeforeClose` restore doesn't reliably stick in that specific
   zero-workbook state. Low real-world impact: normal desktop Excel usage
   quits the whole application when the last window closes, which ends
   the process (and therefore the stuck setting) anyway; the scoped
   Activate/Deactivate pair already handles the actually-common case
   (switching between multiple open files) correctly.
3. **Bump default row height** from Excel's own ~15pt to 19pt —
   `sheet_format.defaultRowHeight`, folded into the same `apply_modern_
   chrome()` helper. **Gotcha found empirically before rolling this out**:
   `defaultRowHeight` alone has *no effect* unless `sheet_format.
   customHeight` is also set `True` on the same sheet — confirmed on a
   throwaway prototype file (row height read back as Excel's own 15pt
   default despite `defaultRowHeight = 19` being set) before it could
   silently no-op across all 12 sheets. Rows with their own explicit
   height (Calendar/Schedule's weekday-header row, Campaigns/Monthly
   Media Plan's taller header row, every Gantt/day-cell row) are
   unaffected, as expected — an explicit `row_dimensions[n].height`
   always wins over the sheet default. Some rows with merged cells or a
   larger font (Dashboard's KPI value row, Calendar/Schedule's weekday
   header) read back a size other than 19pt on reopen despite having no
   explicit height in the file's own XML (confirmed identical
   `sheetFormatPr` across "normal" and "anomalous" sheets by inspecting
   the raw XML) — this is Excel's own auto-fit recalculating a *display*
   height for rows whose content genuinely needs more room than the flat
   default, not a bug in the generated file.
4. **Softer/minimal borders** — accomplished as a side effect of #1's
   hairline-only treatment; no separate work needed.
5. **Bump default zoom** to 115% — `sheet_view.zoomScale`, folded into
   `apply_modern_chrome()` alongside the other three chrome settings.
6. **Dashboard KPI card polish** — replaced the original left-edge
   medium brand-blue border with a **thick brand-blue top accent
   bar** instead (the rest of the card outline downgraded to plain
   hairline `GRIDLINE`), a more current "stat tile" pattern than a
   left-edge color bar — the accent color is now the one clear signal on
   the card rather than competing with itself across multiple colored
   edges. Considered native Excel Sparklines for a "trend at a glance"
   treatment but scoped it out: `openpyxl` has no native write support
   for them (an `x14:` extension outside its object model) and building
   them would mean a new VBA-driven feature (`Range.SparklineGroups.Add`)
   with its own COM test surface — a materially different scope than
   pure visual polish, better considered separately if wanted later.

All six verified together via COM against the freshly rebuilt `.xlsm`:
clean open with `CorruptLoad=0` (no repair prompt) and a zero-error full-
workbook scan (`SpecialCells(xlCellTypeFormulas, xlErrors)` across every
visible sheet) after a full recalc, confirming none of the six changes
introduced a formula regression anywhere.

### 17.11 Post-review fixes (user-reported, PLAN.md §19 Phase 6)

The COM-verified checks above (colors, fonts, cell properties) don't
catch genuine *visual layout* problems the way actually looking at the
rendered file does — the user reviewed the modernized, re-seeded
workbook directly in Excel and reported six concrete issues. Each is a
real bug, not a matter of taste; root-caused and fixed as follows.

1. **Tasks/Archive/Campaigns Archive: `Start Date`/`Deadline`/
   `Completed At` showed `#####`.** Traced to §17.10's own 115% zoom
   bump: these columns use the 16-character `"DD.MM.YYYY HH:MM"` format
   at a column width of 15 — already razor-thin at 100% zoom, and column
   width is stored in fixed character units that don't scale with zoom,
   so the *rendered* pixel width of that same 15-unit column shrinks
   relative to the (now-larger) rendered text at 115%, pushing it into
   overflow. Fixed by widening every column using the 16-character
   date-*time* format from 15 to 19 (`tasks.py`'s Start Date/Deadline,
   `archive.py`'s Start Date/Deadline/Completed At,
   `campaigns_archive.py`'s Completed At) — checked every other date
   column workbook-wide for the same risk while at it: plain
   `"DD.MM.YYYY"` (10 characters) columns all still have enough margin
   at their existing widths and were left alone.
2. **A real, systemic bug found from two separate reports** (Calendar's
   Cancel button "outside of what seems to be a box for it," and
   Schedule's Reminder Settings "also seem to be outside of a box") —
   both are the *same* underlying bug, confirmed by finding the same
   code pattern at both sites (and, on inspection, at four more sites
   that hadn't been reported yet: Dashboard's Refresh Now button and KPI
   cards, Monthly Media Plan's Set Exchange Rate/Start New Month buttons
   and its own KPI cards). **Every one of these bordered "button" cells
   set `.border` only on the merged range's top-left anchor cell.**
   Excel does not copy a merged cell's border from its anchor the way it
   does fill/font — each *physical* cell within the merge contributes its
   own border to whichever outer edge it sits on (the rightmost physical
   cell supplies the right edge, the bottom-most the bottom edge, etc.),
   so a border set on only the anchor renders a box missing its right and
   bottom edges — exactly "sitting outside of what seems to be a box for
   it." Fixed with a new shared `design_system.apply_box_outline(ws,
   cell_range, style, color)`: loops every physical cell in the range and
   gives each cell only the border sides that sit on the range's own
   outer edge (top only on the top row, left only on the left column,
   etc.) — for a single-row/-column merge (every button here) this
   naturally becomes "full border on every cell," the correct fix; for a
   genuine multi-row/-column area it instead produces a clean outline
   with no interior grid lines (unconditionally bordering all 4 sides of
   every cell would draw a visible grid instead). Applied to all six
   sites; Dashboard's and Monthly Media Plan's KPI cards needed a
   hand-written version instead of this shared helper, since their thick-
   blue-top / hairline-elsewhere scheme uses two different border styles
   on the same box, which the shared helper (one style for the whole
   outline) doesn't cover.
3. **Calendar: the live date/time preview text "feels off, in the middle
   of nowhere."** True independent of the border bug above — rows 10-11
   (the Hour/Minute pickers and the preview label beneath them) had *no*
   background or border of their own at all, floating unstyled between
   the day grid above and the Confirm/Cancel buttons below with nothing
   visually tying the three areas together. Fixed by giving rows 10-11 a
   single `CARD_SURFACE` background plus `apply_box_outline()`, the same
   "card" language already used for KPI cards elsewhere — the date/time
   picker now reads as one deliberate panel instead of loose floating
   cells.
4. **Monthly Media Plan: Google/META colors didn't reflect real brand
   colors.** They'd been assigned arbitrary `CATEGORICAL` slots (blue,
   aqua) like any other dropdown field — reasonable by §17.2's own rule
   for an *identity* chip with no external color convention, but Google
   and META very much do have one. Added `design_system.PLATFORM_GOOGLE`
   (`#4285F4`, Google Blue) and `PLATFORM_META` (`#0866FF`, Meta Blue) as
   a second, narrowly-scoped exception to "identity chips always draw
   from `CATEGORICAL`" — the same kind of deliberate exception
   `BRAND_ACCENT` itself already is, per §17.1 — rather than adding them
   to the validated `CATEGORICAL` set itself, whose 8 hues are chosen and
   ordered together as a whole (see `CATEGORICAL`'s own docstring); real
   brand fidelity for exactly this one field isn't the same kind of
   "next available slot" case as `Funded`/`Optimization`/`Recurrence`/
   `Location`. Not re-validated against the `dataviz` skill's CVD
   checker, deliberately — brand-color fidelity is the explicit ask here,
   overriding max-differentiation, and the Platform field always shows
   alongside its own visible text label (never color alone), satisfying
   §17.3's rule regardless.
5. **Dashboard: "Completed tasks by month" and "Hours invested by month"
   overlapped each other, and the Hours chart covered over half of
   Campaign Metrics Summary.** A real, pre-existing layout bug that had
   never been visually caught before — every earlier verification pass
   checked chart *data* correctness (series/colors/values) via COM
   property reads, never actual on-screen position. Root cause: the two
   charts sat side-by-side, anchored at columns A and E, each a fixed
   10cm wide — but Dashboard's own column widths for A-D are reset by
   several *unrelated* sections throughout `build()` (Upcoming Tasks,
   Yearly Monthly Performance, Daily & Weekly Productivity all touch
   columns in this range for their own tables), so the "columns A-D are
   narrower combined than 10cm" assumption the side-by-side layout
   depended on was silently false: the first chart's right edge landed
   ~13px past column E's start (overlapping the second chart), and the
   second chart's own right edge landed **~104px into column H** (~65%
   of that column's width) — exactly where Campaign Metrics Summary
   lives, and at a row already within that section's own range. Fixed by
   stacking both charts vertically in column A instead of side-by-side —
   removes the dependency on any other section's column widths
   entirely, rather than hand-tuning anchor columns/widths to just
   barely avoid the same class of bug recurring the next time a column
   width changes elsewhere on this sheet. The vertical gap between the
   two stacked charts is computed from the sheet's own actual
   `defaultRowHeight` (converting the chart's fixed 6cm height into a row
   count via each row's real point-height, not a hand-tuned magic
   number), so it stays correct even if the default row height changes
   again later.

All six re-verified via COM against the rebuilt file: date-time cells
read back their full formatted text (no `"#####"`) at the new column
widths; every fixed button/card reads a complete 4-edge border across
every physical cell in its merge (`Borders(xlEdgeTop/Bottom/Left/
Right).LineStyle`, checked cell-by-cell, not just the anchor); Google/
META `FormatConditions` read back `#4285F4`/`#0866FF` exactly; and the
two Dashboard charts' actual `ChartObject.Top`/`.Left`/`.Width`/`.Height`
(in points) confirm a genuine ~22pt vertical gap between them and neither
one's horizontal extent reaching anywhere near column H.

### 17.12 Readability pass (user-reported, PLAN.md §19 Phase 6)

A further round after reviewing §17.11's fixes: IDs and several numeric
columns weren't centered, the up/down/Timer cells had no visible
affordance that they're clickable, `Number of Subtasks`' header was

   plain `Cells(r,c).Value = ...` loop (confirmed by reading
   `modHierarchy.bas`'s own rewrite loop) — it never touches fill/
   border/alignment, so a style baked in at a fixed row/column position
   survives any amount of hierarchy reshuffling. Applied to Tasks' and
   Recurring Tasks' up/down/Timer cells (Recurring Tasks has no Timer)

   `Subtask of`, `Days Left`, and `ID` — set on the initial data row

   `Time Spent` column is renamed `Time Spent (hrs)` (same column

### 17.13 Row structure pass (user-reported, PLAN.md §19 Phase 6)

*still* clipping even wrapped onto 2 lines (just a genuinely long label
for the column width available), the whole hierarchy sheets read as

### 17.14 Dynamic button styling + more centering (user-reported, PLAN.md §19 Phase 6)

Project layout (build started — see §19 for live status):

- `sheets/` — one Python module per sheet (e.g. `sheets/dashboard.py`,
  `sheets/tasks.py`, ...), plus shared helpers: `design_system.py` (§17's
  palette/typography/icons), `hierarchy.py` (hierarchy-engine column
  scaffolding), `week_grid.py` (Monday-start month/week formulas),
  `calendar_handoff.py` (the §8.1 handoff's named ranges).
- `sheets/forms/` — **one Python module per UserForm** (`notes_form.py`,
  etc.), each a plain-data spec (control list + properties + code-behind
  string). **Not** `.frm` text files — see the correction below.
- `vba/*.bas` — VBA **standard module** source (plain text): shared
  modules (`modDesignSystem.bas`, `modHierarchy.bas`) and each sheet's
  code-behind. This part of the original plan holds as designed. **File
  naming convention (established in Phase 3):** a `.bas` file named
  exactly after a sheet (e.g. `Tasks.bas`) is injected directly into that
  worksheet's own VBA CodeModule — its `Worksheet_Change`/
  `Worksheet_BeforeDoubleClick` event Subs only fire there — while a
  `modXxx.bas` file (e.g. `modTasks.bas`) is a genuine standard module
  holding the sheet's actual testable business logic, called by the thin
  dispatchers in the sheet-named file. Note that an openpyxl-created
  sheet's VBA **CodeName** (the identifier `inject_vba.py` must target) is
  *not* its visible tab name — openpyxl leaves the auto-assigned default
  (e.g. `Sheet1`) — so injection must look it up via
  `wb.Sheets("Tasks").CodeName`, never assume it literally equals
  `"Tasks"`. **The same is true of the `ThisWorkbook` component itself**
  (target of `vba/ThisWorkbook.bas`, Phase 3) — its VBA name is *also*
  locale-dependent on the build machine (confirmed: `VBComponents("ThisWorkbook")`
  fails outright here), but unlike a sheet it has no tab name to look up
  by. Find it by elimination instead: the one `Type = vbext_ct_Document`
  (100) component whose `Name` isn't any sheet's own `CodeName`.
  `Workbook.CodeName` (the object-level analog of `Worksheet.CodeName`)
  is not a shortcut here — confirmed it returns `""` until the VBA
  project has been touched by at least one `VBComponents.Add` call.
- `inject_vba.py` — COM-based script that opens the generated `.xlsx` in
  Excel, imports the `.bas` modules, **builds each UserForm from its
  `sheets/forms/` spec via VBIDE automation** (see correction below), and
  saves as `.xlsm`.
- `requirements.txt` — `openpyxl`, `pywin32`.

> **Corrected from the original draft, found during Phase 1 implementation
> (live-tested against real Excel, not just reasoned about):** the
> original plan assumed UserForms could be authored as plain `.frm` text
> files the same way `.bas` modules are. They can't. A `.frm` file
> normally pairs with a binary `.frx` file (control positions/properties);
> without a real, Designer-backed `.frx`, `VBComponents.Import()` silently
> accepts the text but misclassifies the component (it doesn't come out as
> a genuine form), so any code that tries to `Load` it fails to compile —
> which then breaks `Application.Run` for *every* macro in the project,
> not just the form-related one. The verified fix: build each UserForm via
> COM automation at injection time instead — `VBComponents.Add(3)` creates
> a genuine form component, `.Designer.Controls.Add(...)` adds real
> controls, `.CodeModule.AddFromString(...)` adds its code-behind. This
> was confirmed to survive save/close/reopen and function correctly.
> UserForm "source" therefore lives as Python specs in `sheets/forms/`,
> consumed by `inject_vba.py`, not as static files in `vba/`.

### Bug #1 — Deadline "today at 18:00" shows "1 day left" instead of "0"

- **Symptom:** user set a task's Deadline to today at 18:00 via the
  Calendar picker (§8.3). `Days Left` showed `1`, not `0`.
- **Root cause:** Tasks' `Days Left` formula (`sheets/tasks.py`, §6.1) was
  `=IF(Deadline="","",Deadline-TODAY())`. `Deadline` is a full datetime —
  the Calendar handoff always writes a picked `Hour`/`Minute` alongside
  the date (§8.3), and a Recurring Tasks generated instance always lands
  at `TimeSerial(18,0,0)` (`modRecurringTasks.bas`, never midnight) — so
  the raw subtraction is a decimal (today 18:00 → `0.75`), and the `"0"`
  number format rounds that decimal *up* for display (`0.75` → `"1"`).
  The countdown is meant to be whole-calendar-day ("due today" = 0,
  regardless of what time today), not a rounded fraction-of-a-day. This
  is systemic, not a one-off: **every** recurring-task instance due today
  would show the same off-by-one, since generated instances always carry
  a non-midnight time-of-day.
  - Not affected: Archive's frozen `Days Left` (`Deadline − Completed At`,
    §7.1) is a genuinely different metric ("days early/late at
    completion") where sub-day precision is meaningful — left as-is.
    Campaigns' `deadline_urgency_rules` conditional formatting (compares a
    raw date cell directly against `TODAY()`/`TODAY()+2` with no
    subtraction step) isn't affected either — only a precomputed,
    rounded-for-display "days remaining" number was.
- **Fix (source):** `sheets/tasks.py` — `days_left_cell.value` now reads
  `=IF(Deadline="","",INT(Deadline)-TODAY())`. `INT()` strips the
  time-of-day off `Deadline` before subtracting, so the result is already
  a whole number — no more rounding ambiguity for the cell itself or for
  anything downstream that reads it (conditional formatting, Dashboard's
  Overdue count, the Dashboard summary block's Days Left lookup, sorting).
  `PLAN.md` §6.1's Days Left row updated to match (corrected-from-original
  blockquote added there).
- **Fix (manual, apply on work laptop):** the `Days Left` column is `M` on
  `Tasks` (`Deadline` is `K`). This is a plain worksheet formula (Tasks
  has no sheet protection), so it's a direct edit + fill-down, no VBA
  editor needed:
  1. Click the **Name Box** (top-left corner, left of the formula bar),
     type `M2`, press **Enter** — jumps to the Days Left cell on row 2.
  2. Type this exact formula and press **Enter**:
     `=IF(K2="","",INT(K2)-TODAY())`
  3. Click the Name Box again, type `M2:M501`, press **Enter** — selects
     the Days Left column for every pre-formatted row.
  4. Press **Ctrl+D** (Fill Down) — copies row 2's formula down through
     row 501, auto-adjusting `K2`→`K3`→`K4`… for each row.
  5. Save (**Ctrl+S**), keep it as a macro-enabled `.xlsm`.
  6. Spot-check: the task due today at 18:00 should now read `0`, and any
     task due tomorrow should read `1`.
  This also silently fixes every future Recurring-Tasks-generated
  instance — those just write into `Deadline` on an already-templated row
  that will now carry the corrected formula.
- **Status:** fix given, awaiting user confirmation after manual apply.

### Bug #2 — Notes icon blank on the first task row, but works from the second row on

- **Symptom:** user filled in Notes for a task; the 📝 icon that's supposed
  to appear didn't show at all (not raw text either — genuinely blank) on
  the first task row, while Notes worked correctly on every row after
  that.
- **Investigation:** the notes-icon masking format (`notes_icon_format()`,
  §6.3) is applied identically to all 500 pre-formatted rows at build
  time, and `RenumberHierarchy` never touches formatting — only values —
  so a display-format theory didn't hold up. Reproduced live via COM on a
  fresh throwaway build (no user data at risk): writing a note directly to
  a plain untasked row and then naming the task in the *same* row worked
  fine. But writing a note to row 2 **before** typing that row's Task
  name, then naming a *different* row's task (which fires
  `RenumberHierarchy`), reliably wiped row 2's note — confirmed via a
  direct before/after read of the cell's value through COM.
- **Root cause:** `modHierarchy.bas`'s `RenumberHierarchy` (§6.2 point 2)
  decides whether a row is "real" data purely by whether its hidden
  TaskKey is non-blank (Pass 1) — a deliberate, already-documented fix for
  a different bug (a truly blank row's key reads back as `0`, colliding
  with the root-node sentinel, `CLAUDE.md`'s hierarchy-engine pitfall
  notes). But TaskKey is only assigned when the **Task** cell itself goes
  from blank to non-blank (`HandleTaskNameChange`'s `isNewRow` block,
  §6.1) — every other field (Notes, Deadline, Timer) can be *reached and
  written to* via double-click before that happens, since none of them
  checked for an existing TaskKey first. A row that receives Notes (or a
  Deadline, or a timer start) while still keyless is exactly the
  "phantom row" `RenumberHierarchy` is designed to skip: the next time
  *any* row's task-naming event fires a renumber, that row's real content
  is silently discarded by `clearRange.ClearContents`, since it was never
  captured into `nodes()` in the first place. This is a genuine gap
  between the sheet's intended lifecycle ("a row isn't really a task
  until you name it," per §6.1's Start Date/TaskKey/Status/Linked
  Campaign defaults all keying off the Task cell) and what the UI
  actually let the user do.
  - Confirmed the identical gap exists on Tasks' **Deadline** and
    **Timer** double-click handlers (`modTasks.HandleDeadlineDoubleClick`/
    `HandleTimerDoubleClick`, neither previously checked for a TaskKey),
    and on **Recurring Tasks'** own Notes double-click (same hierarchy
    engine, same missing guard) — none of these had been hit yet, but all
    share the exact same failure mode, so fixed alongside Bug #2 rather
    than waiting for each to surface separately (per `CLAUDE.md`'s "check
    every instance of this pattern project-wide" precedent).
  - **Deferred, not fixed**: Priority/Project/Linked Campaign are plain
    typed/dropdown cells (no double-click gate to add a guard to) and
    share the same theoretical risk — filling one in before naming the
    task, then triggering a renumber elsewhere, would silently discard it
    too. Not fixed now since it hasn't actually been hit and would need a
    new Data-Validation-based gate (more invasive) rather than a one-line
    guard; flagging here so it's not forgotten if it ever surfaces.
- **Fix (source):** `vba/Tasks.bas` — Deadline (col 11), Timer (col 14),
  and Notes (col 16) double-click cases now check `Target.Worksheet.Cells
  (Target.Row, 17)` (hidden TaskKey) first; if blank, shows `"Type the
  task name first, then …"` and does nothing, instead of proceeding.
  `vba/Recurring Tasks.bas` — same guard added to its Notes case (col 14),
  checking column 15 (hidden RecurringKey). Rebuilt and re-injected on the
  build machine to confirm the VBA project still compiles clean; re-tested
  via COM that Notes still works normally on an already-named task
  (unaffected by the guard).
- **Fix (manual, apply on work laptop):** this one **is** VBA, so it goes
  through the VBA editor (Alt+F11), not a worksheet cell edit:
  1. Press **Alt+F11** to open the VBA editor.
  2. In the Project Explorer (left pane), under
     `VBAProject (Performance Marketing Dashboard.xlsm)` → `Microsoft
     Excel Objects`, double-click **Tasks** to open its code module.
  3. Find the `Worksheet_BeforeDoubleClick` sub. Replace the three
     `Case 11`, `Case 14`, `Case 16` blocks with:
     ```vba
     Case 11   ' Deadline
         If Len(Trim$(Target.Worksheet.Cells(Target.Row, 17).Value & "")) = 0 Then
             MsgBox "Type the task name first, then set a deadline.", vbInformation, "No task yet"
         Else
             modTasks.HandleDeadlineDoubleClick Target.Row
         End If
         Cancel = True
     Case 14   ' Timer
         If Len(Trim$(Target.Worksheet.Cells(Target.Row, 17).Value & "")) = 0 Then
             MsgBox "Type the task name first, then start the timer.", vbInformation, "No task yet"
         Else
             modTasks.HandleTimerDoubleClick Target.Row
         End If
         Cancel = True
     Case 16   ' Notes
         If Len(Trim$(Target.Worksheet.Cells(Target.Row, 17).Value & "")) = 0 Then
             MsgBox "Type the task name first, then add notes.", vbInformation, "No task yet"
         Else
             frmNotes.ShowForCell Target
         End If
         Cancel = True
     ```
  4. In the Project Explorer, double-click **Recurring Tasks** to open its
     code module. Find its `Worksheet_BeforeDoubleClick` sub and replace
     its `Case 14` block with:
     ```vba
     Case 14   ' Notes
         If Len(Trim$(Target.Worksheet.Cells(Target.Row, 15).Value & "")) = 0 Then
             MsgBox "Type the task name first, then add notes.", vbInformation, "No task yet"
         Else
             frmNotes.ShowForCell Target
         End If

     ```
  5. Press **Ctrl+S** to save (keep it `.xlsm`). Close the VBA editor.
  6. **Recovering the row you already lost notes on:** this fix only
