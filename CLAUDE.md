This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This repository is **fully implemented and past handoff** — `build_dashboard.py`, `sheets/*.py`, `vba/*.bas`, `inject_vba.py` all exist, and a committed `Performance Marketing Dashboard.xlsm`/`.xlsx` template is checked in. The project is in **post-handoff maintenance mode**: the user has a separate, real, actively-used copy of the workbook on a work laptop (not this repo's committed file). **As of 2026-08-17 the delivery model changed** (PLAN.md §21): rather than continuing to hand-edit that live file cell-by-cell/module-by-module forever, the user's laptop copy hit Tasks' row ceiling and they asked for a freshly rebuilt workbook ("V3") plus a self-service migration tool (`vba/modMigration.bas`, ships in every build) that copies their real data out of the old file and into the new one **entirely on their own machine** (their data is confidential/internal-network-only, so it never passes through this session). The day-to-day work here is still mostly diagnosing and fixing bugs, just delivered as "rebuild + let the user migrate" going forward rather than exclusively as manual line-edit instructions — see PLAN.md §21 for the full design and CLAUDE.md's own `Application.Run` qualification gotcha below, found while testing it. **Before doing anything, check `PROGRESS.md`** (repo root) for a quick "where we left off" status and any pending next steps — it's a short pointer, not a substitute for reading further.

`PLAN.md` is the single source of truth for every design decision made so far, including everything already built. It is kept scannable via numbered sections (`## 1.` … ) with `[[Section Name]]`-style cross-references between them. **Before making any change to this project, read the relevant sections of `PLAN.md`** — decisions in later sections sometimes correct or supersede earlier ones (each correction is called out inline with a `> **Corrected from the original draft**` blockquote), so the most recent text in a section is authoritative, not the first mention of a topic. §19 is the (now-complete) build checklist; **§20 ("Debugging log, post-handoff") is the actively-growing log of bugs found on the live work-laptop file since handoff** — read it before diagnosing anything reported against that file, since a fix may already be documented there (including ones the user hasn't confirmed applying yet — check the `Status` field of each entry).

If asked to plan a genuinely new sheet or feature (rare at this stage), follow the same pattern already established throughout `PLAN.md`: confirm genuinely ambiguous design forks with the user before locking them in, document *why* a decision was made (not just what it is), and flag any technical necessity that goes beyond what the user literally asked for (e.g. hidden helper columns, stable keys) as such.

## What this project is

A personal, single-user Excel workbook — an "app-like" interactive task tracker and dashboard for a performance marketing role, replacing scattered spreadsheets. Full functional scope (Dashboard, Tasks, Archive, Calendar, Campaigns, Campaigns Archive, Monthly Media Plan, Recurring Tasks, Schedule + Schedule Data, Login Information, Quick Links, Instructions, plus an internal-only `Time Log` sheet) is defined in `PLAN.md` — see its §2 Sheet Index for status of each.

## Key constraints (see `PLAN.md` §1 for full detail)

- **Target Excel version: 2016 / 2019.** No dynamic arrays, no `XLOOKUP`/`FILTER`/`UNIQUE`/`SORT`/`LAMBDA`. Formulas must stay legacy-safe: `INDEX`/`MATCH`, `SUMIFS`/`COUNTIFS`, `SMALL`/`LARGE`, and real Excel Tables (ListObjects) for structured references.
- **VBA macros are allowed** (final workbook is `.xlsm`) but used only where formulas genuinely can't do the job (buttons, popups, cross-sheet automation) — the core data layer is formula-driven wherever possible.
- **Build approach (planned, not yet implemented):** the workbook will be generated by a Python script using `openpyxl` for structure/formulas/formatting, since `openpyxl` cannot write VBA. Macro injection will be a separate step using `pywin32` (COM automation driving a locally installed Excel), which requires "Trust access to the VBA project object model" enabled once in Excel's Trust Center on the machine used to build the file.
- **Planned project layout** (per `PLAN.md` §18, none of this exists yet): `build_dashboard.py` orchestrator, one Python module per sheet under `sheets/`, VBA module source under `vba/*.bas`, `inject_vba.py` for the COM-based injection step, `requirements.txt` (`openpyxl`, `pywin32`).
- **Visual design system (`PLAN.md` §17):** all color, typography, and iconography is centralized there rather than per-sheet — a validated palette (categorical/status/sequential/diverging color "jobs," each chosen for accessibility rather than eyeballed) plus a brand accent kept deliberately separate from the data-encoding palette. When implementing or planning any sheet's formatting, pull values from §17 rather than inventing new colors/icons — several earlier sheet sections were already retroactively corrected to match it (e.g. Tasks §6.1/§6.4, Archive §7.1).

## Testing VBA via COM automation

Implementation (Phase 1 onward, per §19) is routinely verified by driving
real Excel through `pywin32` rather than just reasoning about VBA
statically — this has repeatedly caught real bugs a code review would
have missed (a numeric-ID text-format bug, the `.frm`/`.frx` UserForm
limitation, a sheet-protection/`ListObject` interaction). Keep doing this.

**Critical rule: every VBA `Function`/`Sub` invoked via `Application.Run`
during a test must have a top-level `On Error GoTo ErrHandler` that
captures `Err.Number`/`Err.Description` into the return value and never
lets an error propagate unhandled.** `Application.Visible = False` and
`DisplayAlerts = False` do **not** suppress VBA's own runtime-error
dialog — an unhandled error still pops up a blocking, modal "Run-time
error" window on the user's actual screen that only a manual click can
dismiss, regardless of the automation's visibility settings. This has
actually happened and interrupted the user — treat it as a hard
requirement for every test driver, not a nice-to-have.

Other lessons learned the hard way, worth not re-learning:
- The test machine's Excel is Bulgarian-locale. Verify numeric/date
  results via their native COM type (a real `float`/`Date`) or by
  decomposing a date into `Year()`/`Month()`/`Day()`, never via
  locale-formatted string concatenation (`"1,5"` is `1.5`; dates render
  as `20.7.2026 г.`) — apparent mismatches here are usually false
  negatives, not real bugs.
- Track any launched Excel process's PID at launch (`GetWindowThreadProcessId`)
  and kill it explicitly in a `finally` block. Never `taskkill` a PID
  discovered via a system-wide `tasklist` scan without having tracked it
  yourself at launch — the safety layer will (correctly) block that, since
  it can't be verified as the agent's own process rather than the user's.
- Clean up every test's temp files and confirm zero `EXCEL.EXE` processes
  remain (`tasklist`) before considering a test round finished.
- For conditional-formatting fills, openpyxl's `PatternFill("solid",
  fgColor=...)` silently renders as black/no-color in real Excel —
  `fgColor` is ignored for a *differential* (CF) fill the way it isn't for
  a normal cell style; use `bgColor` instead (`Interior.Color` reads back
  `0` otherwise). This was project-wide and undetected for several phases
  before a live `Interior.Color` check on the Gantt bars caught it — see
  `sheets/conditional_formatting.py`'s `_fill()` and PLAN.md §19's 2G
  correction note. Verify a CF fill's *rule definition* directly
  (`FormatConditions(n).Interior.Color` / `.Formula1`), not
  `DisplayFormat.Interior.Color` — already known unreliable for fills when
  Excel is invisible/headless (see the 2E correction note).
- **The exact opposite is true for CF *borders***: `FormatConditions(n)
  .Borders(edge)` throws "cannot read the LineStyle property from the
  Border class" via COM even when the border is defined correctly and
  genuinely renders — confirmed by writing an isolated prototype file and
  testing three separate `Border` constructions (uniform 4 sides, mixed
  sides/styles, one side only) side by side; all three threw the
  identical error when queried this way, yet all three rendered fine.
  Verify a CF border via the *target cell's own* `DisplayFormat.Borders
  (edge)` instead — reliably correct here, unlike the fill case above
  (PLAN.md §19 Phase 6, Dashboard's Current Campaign Ends KPI card
  indicator). Don't assume a CF border "isn't applying" from a
  `FormatConditions(n).Borders` read failing — it's the query that's
  broken, not necessarily the rule.
- TEXT()'s format-code argument is parsed against the current Excel
  locale's own decimal separator, not a fixed period — `TEXT(x,"0.00")`
  errors (`#VALUE!`) on a comma-decimal locale. Use `FIXED(x, decimals)`
  instead when formatting a number as display text; it has no format-code
  string to mismatch.
- **A CSE-free array formula (`AGGREGATE`, `SUMPRODUCT`, etc.) can compute
  correctly when entered fresh via VBA but silently wrong/erroring when
  the identical text is written by `openpyxl` and read back after a clean
  open + full recalc** (`Application.Calculate` *and*
  `Application.CalculateFullRebuild` both insufficient in the confirmed
  case) — only an actual VBA rewrite of the cell fixed it. Don't assume
  "computes right when I test it via VBA" proves an openpyxl-authored
  array formula is safe; test it on a freshly-built, never-VBA-touched
  file specifically. `SUMPRODUCT(MIN(...))`/`SUMPRODUCT(MAX(...))` was
  reliable where `AGGREGATE` wasn't (Dashboard §4.A).
- Inside a `SUMPRODUCT(...)`-forced array context, **bare arithmetic
  operators on a range vectorize correctly, but a function call wrapping
  that range (`N(range)`, `IF(ISNUMBER(range),range,0)`) can silently
  collapse to evaluating only the range's first cell** instead of
  per-element — confirmed via COM by comparing the result to what the
  top-left cell alone would produce. If a range needs text/blank
  coercion inside such a formula, don't nest a coercion function around
  it; restructure to avoid needing coercion at all (Dashboard §4.A reused
  an already-safe helper column instead).
- `SUMPRODUCT`/`MIN`/`MAX` cannot skip an error mid-array the way
  `AGGREGATE`'s error-ignore option can — one `#VALUE!` (e.g. from
  arithmetic on a cell that holds `IFERROR(...,"")`'s empty-string
  fallback, not a genuinely blank cell) poisons the whole result. Check
  whether a "blank" cell in a shared/reused column is actually a formula
  returning `""` before doing arithmetic on it across a range.
- **`.End(xlUp)` silently returns the last *visible* row, not the true
  last row, when the actual last row is hidden** — confirmed via COM: a
  collapsed row's cell values read back correctly via direct access, but
  `.End(xlUp).Row` reported the row above it, as if the hidden row didn't
  exist. Any hierarchy-engine or list-scanning code that needs "the true
  last data row" must use a manual scan instead (`modHierarchy.bas`'s
  `LastHierarchyRow`), never `.End(xlUp)`, whenever the data being scanned
  can ever be individually row-hidden (collapse/expand being the obvious
  case, but worth checking for any sheet with a `Rows.Hidden` toggle).
  **The same failure mode exists on the column axis, `.End(xlToLeft)`
  vs. hidden columns** — found in `modCalendarHandoff.bas`'s
  `FindColumnByHeader`, which used `.End(xlToLeft)` to find a sheet's
  last header column and silently stopped at the last *visible* one,
  never reaching a hidden header like Tasks' `TaskKey`. This one bit
  harder than the row case: a hierarchy sheet's key/parent-key columns
  are hidden *by design*, so every real call into this function hit the
  bug, not just a rare collapsed-row edge case. Whenever code searches
  for "the last column/row with data" on a sheet that hides *anything*
  structurally (not just via a user action), assume `.End()` is unsafe
  on that axis and use a manual scan to a generous fixed bound instead.
- **A whole-row `Rows(r).Delete` errors outright when that row is shared
  by two independent Tables in different columns** (e.g. `Schedule
  Data`'s `WorkLocationTable` in A:B and `MeetingsTable` in D:J sitting
  on the same physical row numbers) — Excel refuses the operation rather
  than silently restructuring both. Delete through the specific Table's
  own `ListRows` collection instead (`tbl.ListRows(rowIndexWithinTable).Delete`),
  which only touches that Table's own column range. Any sheet with
  side-by-side Tables sharing row-number space needs row-scoped deletion
  logic to go through the right Table object, never a raw `Rows().Delete`.
- **A hierarchy engine that treats "row's key cell reads back as `0`" the
  same as "this row is genuinely blank" will misfire**, because
  `CDbl(Empty)` (a truly blank cell) also equals `0` — and `0` is a
  natural choice for a "root/no-parent" sentinel value. If a walk/
  recursion uses that same `0` to mean "no parent," a blank row
  masquerading as a zero-keyed node can send the recursion back into its
  own parent group, growing an output index past its allocated size
  ("Subscript out of range"). Fix at the source: skip rows with a
  genuinely blank key entirely during the initial snapshot pass, rather
  than adding bounds-checking downstream — this also has the side benefit
  of self-healing any gap by compacting real data back to the top instead
  of merely tolerating the hole (`modHierarchy.bas`'s `RenumberHierarchy`,
  PLAN.md §19 Phase 1 correction note). Don't dismiss a "blank rows in the
  middle of the data" scenario as a test-only artifact without checking
  whether the sheet is a pre-formatted Table with many rows available for
  non-contiguous entry — for this project's `Tasks`/`Recurring Tasks` it
  is, so it's a real production risk, not just a test setup quirk.
- When a bug's root cause isn't obvious from re-reading the code, **add
  throwaway checkpoint tracing directly in the VBA** (a module-level
  `Public gDebugTrace As String`, appended to after each major step, read
  back by the test's own `ErrHandler`) rather than guessing from repeated
  manual code tracing — it converges faster and with more confidence.
  Remove the instrumentation once the root cause is confirmed and fixed;
  don't leave debug scaffolding in shipped modules. (Pitfall hit while
  doing this: a module-level `Public`/`Dim` declaration must be grouped
  with the module's other top-level declarations, not inserted between
  two `Sub`/`Function` blocks lower down — doing so broke the whole VBA
  project's compilation, which surfaced as a generic COM exception on
  `Application.Run` instead of a normal caught VBA runtime error.)
- An openpyxl-created sheet's VBA **CodeName is not its visible tab
  name** — openpyxl leaves the auto-assigned default (e.g. `Sheet1`), so
  code injecting directly into a sheet's own module (rather than a
  standalone standard module) must look it up via
  `wb.Sheets("Tasks").CodeName`, never assume it literally equals the tab
  text. **The `ThisWorkbook` component has the exact same problem, but
  worse** — its own VBA name is *also* locale-dependent on this Bulgarian-
  locale build machine (`VBComponents("ThisWorkbook")` fails with
  "Subscript out of range" on a fresh, never-previously-VBA-touched
  workbook), and unlike a sheet it has no tab name to look it up by.
  Fixed by elimination: the one `Type = vbext_ct_Document` (100)
  component whose `Name` isn't any sheet's own `CodeName`. Also confirmed
  `Workbook.CodeName` (the object-level analog of `Worksheet.CodeName`)
  isn't a shortcut — it returns `""` until the VBA project has been
  touched by at least one `VBComponents.Add` call, so `Worksheet.CodeName`
  queries made *before* adding any component also come back empty; always
  add at least one component first.
- **Testing a reserved auto-fired event Sub (`Workbook_Open`,
  `Workbook_BeforeClose`) requires an actual close→reopen cycle** —
  they're not ordinary callable procedures, so `Application.Run` can't
  invoke them directly the way it can a regular `Public Sub`. Save as a
  genuine macro-enabled `.xlsm` (`FileFormat:=52`) before closing — a
  plain `.xlsx` save silently strips the VBA project — then reopen that
  file; Excel fires `Workbook_Open` automatically, the same as it would
  for a real user. Verify each constituent action's *effect* after
  reopening (a write succeeding on a supposedly-protected sheet, a
  freshly generated row, a real scheduled timer), not by re-invoking the
  constituent functions directly, since those are typically already
  unit-tested in their own phase and re-testing them here would only
  prove the functions work, not that the event actually triggers them.
- **A `Private Sub` event handler (`Worksheet_Change`/
  `Worksheet_BeforeDoubleClick`) cannot be invoked via `Application.Run`
  at all, regardless of qualifier syntax** — confirmed via COM: it fails
  with "Cannot run the macro... may not be available in this workbook,"
  a hard VBA visibility rule, not the blocking-modal problem that
  motivates splitting risky logic out of a dispatcher (`CascadeDelete`/
  `WouldCreateCycle` etc.). This is *why* every sheet's thin dispatcher in
  this project has been verified by code review rather than direct
  invocation, not an oversight — there is no way to drive one directly.
  Test the substantive logic a dispatcher routes to instead (the
  established pattern all along); if a dispatcher truly has no logic
  beyond a single built-in call (Dashboard's Refresh Now button), the
  most that's independently verifiable is that the whole VBA project
  still compiles with it injected, plus the built-in call's own effect
  tested decoupled from the unreachable wrapper.
- **`Worksheet_BeforeDoubleClick`'s `Target` is never a broader multi-cell
  *selection* — a guard like `If Target.Cells.Count > 1 Then Exit Sub` at
  the top of the dispatcher is based on a false premise and will silently
  swallow every double-click on a *merged* cell**, since `Target` for a
  merged cell is its whole merge area (legitimately `Cells.Count > 1`).
  Found live (real Phase 5 manual testing, not COM) after this guard had
  been silently breaking every merged-cell button in the workbook
  (Calendar's Confirm/Cancel, Monthly Media Plan's two buttons,
  Schedule's Reminder Settings, Dashboard's Refresh Now) since Phase 3 —
  COM testing never caught it because a `Private Sub` dispatcher can't be
  invoked via `Application.Run` at all (see above), so this exact bug was
  structurally unreachable by any test in this project until a human
  actually double-clicked the button. `Worksheet_Change` is different —
  a paste/fill genuinely can span multiple cells there, so the same guard
  is correct in that handler and should stay.
- **VBA's own source-code text is stored using the system's ANSI
  codepage, not Unicode — a Unicode character embedded as a literal
  string *inside VBA source code* silently corrupts to "?" the moment
  the module compiles, on any machine whose codepage can't represent it**
  (confirmed live: this Bulgarian-locale/Windows-1251 machine can't
  represent any of this project's dingbat/emoji icon glyphs). This is a
  *compile-time* VBE limitation, unrelated to how the code gets there
  (`AddFromString` via COM behaves identically to typing it by hand) and
  unrelated to Unicode handling at runtime, which is fine. It does NOT
  affect any icon written by openpyxl directly into a cell (real Unicode
  XML, never touches VBA source text) — only a glyph that's a literal
  string constant *inside* a `.bas` file is at risk. Fix: never embed the
  raw character; build it at runtime via `ChrW(codepoint)` instead (a
  numeric literal is plain ASCII, so it's immune) — concatenate two
  `ChrW()` calls (a UTF-16 surrogate pair) for any supplementary-plane
  character (most emoji, codepoint above U+FFFF). A `Const` can't hold a
  function-call result, so this also means converting any affected icon
  constant into a parameterless `Function` instead — every existing
  call site keeps working unchanged, since VBA auto-invokes a zero-arg
  `Function` referenced by name in an expression, same as a `Const`.
- **The same corruption also happens through a completely different
  pathway: typing or pasting a supplementary-plane Unicode character
  (most emoji) directly into a native Windows dialog box's text field —
  not just compiling VBA source.** Found live (post-handoff debugging,
  PLAN.md §20 bug #3, on the user's own work laptop, a different machine
  from the Bulgarian-locale build machine above): pasting the Notes 📝
  icon into Format Cells > Custom's Type field *looked* correct in the
  dialog, but a live VBA diagnostic afterward (`Selection.NumberFormat`)
  showed the saved format code actually contained two literal `?`
  characters — one per UTF-16 surrogate-pair unit — not the emoji. This
  is why it's worth checking for on *any* machine, not just this specific
  locale: most default Windows ANSI codepages (not only Cyrillic ones)
  can't represent emoji. Same fix as the VBA-source case: never type/
  paste the raw glyph into a dialog box; build it at runtime with
  `ChrW()` and assign it through the VBA object model instead (e.g.
  `Range(...).NumberFormat = "General;General;General;" & Chr(34) &
  ChrW(55357) & ChrW(56541) & Chr(34)`, run from the Immediate Window) —
  the assignment line itself is then pure ASCII, so nothing in it can be
  mangled in transit. Doesn't affect anything `openpyxl` writes directly
  into a cell/style at build time (real UTF-8 XML, never touches a
  Windows dialog control) — only content a human types or pastes through
  a native UI control on the affected machine is at risk.
- Two already-documented bug *classes* recurred on sheets they hadn't
  been checked on yet, worth remembering as "check every instance of this
  pattern project-wide the first time you fix one," not just the one
  column/sheet that happened to surface it first: (1) a self-healing,
  position-relative live formula column left out of
  `RenumberHierarchy`'s exclusion list (`Days Left` this time, alongside
  the already-known `Number of Subtasks`) gets silently clobbered into a
  frozen static value on every renumber; (2) a Table that starts with one
  pre-allocated blank data row (the established "minimum valid size"
  convention) leaves that row permanently empty if the append logic
  always does a raw `ListRows.Add` instead of checking "is this still the
  untouched template row" first (`Archive` this time, alongside the
  already-known `Schedule Data`/`Campaigns Archive` pattern).
- **`Range.Replace` has no `LookIn` parameter** (that belongs to
  `Range.Find` only). Passing `LookIn:=xlFormulas` as a named argument to
  `.Replace()` does not raise a compile error when the code is injected
  at runtime via `CodeModule.AddFromString` (unlike a statically-compiled
  module, where the VBE would flag it immediately) — instead, calling
  that Sub/Function via `Application.Run` **hangs indefinitely**, with no
  error, no exception, and `Application.Ready`/`CalculationState` both
  reporting the app as idle the whole time (ruling out both a blocking
  modal and an actively-running loop as the apparent cause). This cost a
  large number of bisected test runs before the bad parameter was spotted
  by diffing two otherwise-identical macros line by line. When a
  `Run`-invoked macro hangs with those symptoms, suspect an invalid named
  argument on whatever Excel object-model call sits at the exact line
  checkpoint-tracing narrows it to (PLAN.md §20's Bug entries have a
  worked example) — don't assume a hang implies bad data or an infinite
  loop; verify every named parameter actually exists on that method's
  real signature first.
- A migration/extension test that seeds its "donor" row with only plain
  values (bypassing events, to avoid triggering the hierarchy engine
  mid-setup) can miss a real bug if that sheet also has **dynamic
  per-row styling applied only conditionally at runtime**, separate from
  the sheet's static "generous pre-formatted allowance" (e.g. Tasks'
  Up/Down/Timer "button" look, applied only to rows holding a real task
  via `RefreshButtonStyling`, never baked in at build time). A donor row
  that's realistically "at capacity" already has that dynamic styling
  applied; a test that seeds only bare values doesn't, so copying that
  row's format in the test looks safe when the same copy on a real
  at-capacity row bleeds the button styling onto every new blank row.
  Explicitly exercise a sheet's dynamic runtime styling on the donor row
  before copying its format in any such test, not just its values.
- **`Application.Run("Module.Proc", args...)` fails with "the macro may
  not be available in this workbook" the instant a SECOND workbook is
  open — even a plain `.xlsx` with no VBA project at all — regardless of
  argument types or which workbook is active.** Confirmed live while
  testing `modMigration.bas` (PLAN.md §21, the only module so far that
  legitimately needs two workbooks open at once): the unqualified
  `"ModuleName.ProcName"` form only reliably resolves when exactly one
  workbook is open; fully qualifying it with the macro-host workbook's
  name (`"'" & wb.Name & "'!ModuleName.ProcName"`) fixed it immediately,
  with no other change. This only affects **test harnesses driving VBA
  via COM from outside** — real in-VBA calls between Subs in the same
  project (e.g. `modMigration`'s own `MigrateFromV2` calling
  `MigrateTasksAndArchive srcWb` directly, never through
  `Application.Run`) are completely unaffected, since that's an ordinary
  same-project procedure call, not macro-name resolution. Whenever a COM
  test needs `Workbooks.Open` on a second file (a migration/import
  feature, a "compare against a fixture" test, etc.), qualify every
  `Application.Run` call with the host workbook's name from the start
  rather than debugging a generic "macro not available" error the slow
  way.
- **A `.bas` file's `Attribute VB_Name = "..."` line must be stripped
  before `CodeModule.AddFromString` whenever the component's `.Name` is
  already set via the VBIDE API (`VBComponents.Add` + `comp.Name = ...`),
  or the whole VBA project's compiled state silently corrupts — breaking
  `Application.Run` for *every* macro in the project, not just the newly
  added one, and producing the exact same generic "macro may not be
  available in this workbook... all macros may be disabled" error as the
  Trust Center/second-workbook issues above.** Confirmed live via an
  extended debugging session that initially (wrongly) suspected Trust
  Center settings: `VBAWarnings`/`AccessVBOM`/`AutomationSecurity` were
  all already correct, a trivial one-line macro reproduced the failure
  from a bare `Workbooks.Add()` workbook every time, and — the decisive
  clue — calling a function that already worked fine (pre-existing in a
  previously-built, previously-compiled `.xlsm`) started failing too the
  moment a single unrelated `VBComponents.Add` call touched that same
  project, even though the newly-added module was never itself invoked.
  `inject_vba.py` already does this correctly (`_strip_attribute_line`,
  used on every `_read_bas()` call before `AddFromString`) — this bit
  only because a throwaway COM test script fed `AddFromString` the raw
  `.bas` text (Attribute line intact) after already setting `comp.Name`
  explicitly. Any new test harness that injects VBA via `AddFromString`
  must strip that line the same way, or risk a long, misleading detour
  into Trust Center registry settings that were never the actual problem.
- **Seed at least TWO rows into any Table that starts with a blank
  "starter" row before trusting a test of code that appends to it.** The
  first append reuses the starter row (`NextArchiveRow`/`NextTableRow`)
  and never calls `ListRows.Add`, so a one-row fixture can't hit any
  failure that only `ListRows.Add` has -- most importantly "Table
  functions are not available because the sheet is protected" (1004),
  which `UserInterfaceOnly` does NOT prevent (PLAN.md §7.1). This hid the
  V2→V3 migration bug for two months: every fixture had exactly one
  archived row; the user's real file had many (PLAN.md §22.9). Any code
  that appends to Archive/Campaigns Archive outside the existing cascades
  must `Unprotect` → append → `Protect UserInterfaceOnly:=True` itself.
- **Pass dates to VBA from Python as Excel serial numbers, not
  `datetime` objects.** pywin32 converted a naive midnight `datetime` via
  the local timezone and VBA received 21:00 the previous day -- which
  looked exactly like an off-by-one-day bug in the code under test
  (`harness.serial()` in the V4 test scripts).
- **Excel's "ignore this error" flag (the green number-stored-as-text
  triangle) is per cell and is CLEARED whenever that cell's value is
  rewritten** -- confirmed via COM. So it can't be set once at build time
  for any column the hierarchy engine rewrites (ID, Subtask of): re-apply
  `modDesignSystem.HideNumberAsTextFlag` per cell after every renumber.
  (openpyxl also models `<ignoredErrors>` but never writes it; a manual
  XML patch worked but was pointless for the reason above, and putting
  the element in the wrong position -- after `<tableParts>` -- made
  Excel refuse to open the file at all.) `Range.Errors` also fails on a
  multi-cell range; loop single cells.

## Recurring architectural patterns established across sheets

Several mechanisms get reused deliberately across multiple sheets rather than reinvented — when planning or building a new sheet, check whether one of these already fits before designing something new:

- **Stable hidden keys** (e.g. `TaskKey`, `CampaignKey`): monotonic, never-reused identifiers for cross-sheet or hierarchical references, since user-visible IDs/names can shift.
- **Hierarchy engine** (`Tasks`, `Recurring Tasks`): unlimited-depth subtasks via hidden `ParentKey`/`Level`/`SiblingOrder` columns and a `RenumberHierarchy()`-style routine that rebuilds visible IDs and row order from scratch on every structural change — cascading renumbering is a side effect of this, not a separate mechanism.
- **Archive-on-complete**: a `Status → Completed` change cascades a copy (as static values, not formulas) to a paired flat "Archive" sheet, freezing any live/time-based fields at that moment.
- **Popup UserForms** for anything too rich for a plain cell (multi-line notes, exchange rate entry, date+time pickers), generally reusing an existing form's pattern rather than inventing new interaction language.
- **`Worksheet_BeforeDoubleClick`/`Worksheet_Change` dispatchers**: one dispatcher per sheet, branching by column — new interactive columns get a new branch, not a new handler.
- **Sheet code-behind vs. standard module**: a `vba/*.bas` file named exactly after a sheet (e.g. `Tasks.bas`) is injected directly into that worksheet's own VBA CodeModule and holds only thin dispatchers; a `modXxx.bas` file (e.g. `modTasks.bas`) is a genuine standard module holding the actual testable business logic, one `Public Function`/`Sub` per handler.
- **`MsgBox`-bypass testing pattern**: any function whose production path shows a confirmation/error `MsgBox` (e.g. delete confirmation, cycle rejection) needs its core logic split out into a separate `Public` function/sub that a test can call directly, bypassing the modal — established first for `frmNotes`' `ShowForCell`/`PrepareForCell` split, reused for Tasks' `CascadeDelete` and `WouldCreateCycle`.
